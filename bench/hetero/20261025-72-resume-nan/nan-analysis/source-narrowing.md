## Numeric exclusions and candidates

1. `kernels.cu:1491-1525`: all-finite router logits cannot produce softmax NaN through underflow. Subtract-max leaves at least one exp(0)=1. The full sum is at least one. Top10 includes the largest probability, so selected_sum is at least 1/E (1/512 here), above the 6.103515625e-5 floor. This does not address already nonfinite logits or memory corruption.
2. `kernels.cu:136,266` writes mixed_h with unsaturated `hf(s)`, although the parallel mixed FP32 and BF16 images can remain finite. `prefill.cpp:2932,2937` feeds mixed_h into shared gate/up native projection. A NaN caused there cannot be repaired by the later SwiGLU hf_sat. This is a concrete candidate only if the detailed scan finds nonfinite mixed_h at the affected token. An FP16 round-to-nearest overflow begins at magnitude 65520; the largest finite FP16 number is 65504. A minimum host fixture should use finite input 65536, weights containing +1/-1 (or zero), and demonstrate inf/-inf cancellation (or inf*0) produces NaN in the simulated projection while the FP32 reference is finite. Include an unaffected second row to reproduce row-local poisoning. Do not call a synthetic reproduction evidence that the real row exceeds that range.
3. The normal FP16 routed path has a strong bound: with all finite FP16 X and weights, GU accumulation magnitude is at most 2560*65504^2, about 1.10e13. The SwiGLU product is below about 1.21e26 and hf_sat limits Hh to 65504. Down accumulation is at most 640*65504^2, about 2.75e12. These bounds are far below FLT_MAX. Shared projections have the same FP16/FP32 arithmetic contract. Thus if all consumed FP16 images and dequantized weights are finite, simple FP32 overflow is not an explanation for this fallback path. Inspect layout, stale scratch, stream/event ordering, or the actual GEMM implementation when a finite-to-NaN boundary appears there. `gemm.cu:819-875` native projection dequantizes to FP16, then `gemm.cu:706-710` uses FP32 compute and FP32 output on CUDA.
4. Distinct latent MMQ issue, probably inapplicable to layer45 with this build: `moe_mmq.cu:87-96` leaves SwiGLU in FP32, then `prefill.cpp:3800` quantizes it. Pinned `quantize.cu:549` stores DS4 scale AND 32-value partial sum in FP16; 32 finite values of 2048 yield partial sum 65536 and an infinite stored sum, despite finite H. D2S6 has a similar 16-value sum. `mmq.cuh:60-96` selects layouts by weight type: Q4_K/Q5_1 use DS4; many IQ types use D4 with FP32 scales and no partial sum. Do not generalize half-scale overflow to all Q8/MMQ formats. A fixture can emulate the reductions and half rounding for these exact layouts without a GPU, but this is not the primary layer45 candidate while KQUANTS is OFF.
