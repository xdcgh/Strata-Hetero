# Run51 direct regression review

This read-only audit compares run51’s stopped `w10-all / quality-on` arm with the complete nine-prompt run41 baseline. It extracts `strata_diagnostics.actual_generated_token_ids` from the preserved final SSE event objects; it does not re-tokenize visible text. The executable audit is [audit_run51_vs_run41.py](audit_run51_vs_run41.py), and its result is [run51-vs-run41-evidence.json](run51-vs-run41-evidence.json) (SHA-256 `fd3697b40b034919d1f71daaee78c952de3ab396adb9f40f9c96b386ddf1c621`).

Run51 passed its first five prompts. Every warmup and all three formal responses for those prompts have the same actual token-ID hash as run41’s H4 reference. Run51 stopped on `long_1k`: its warmup and three formal responses each emitted 128 token IDs, all ID `0`, with canonical ID-array SHA-256 `1b912946d3fd584649a7924a6d699d2bd0ee0da2ebc320bd53135fa9b1ec21a0`. Each formal response finished with `length` and displayed 128 `!` bytes. Run41’s three successful `long_1k` formals emitted 84 IDs and match H4 hash `51ea5b6dcea27d599ff6e68093486be46b29af9b06c2f57677cc27bc0f90099b`. This is a directly observed long-prompt regression in run51; it does not identify a cause.

The `long_1k` prompt bytes and SHA-256 are identical across the runs, and both tokenize locally to 1,036 chat tokens. Both used a 128-token cap; all observed requests report `cached_tokens: 0`. The first five prompts also have identical prompt hashes, local chat-token counts, caps, actual H4 IDs, and zero cached prompt tokens. Both configurations use temperature 0, top-p 1, seed 42, one request slot, max context 32,768, int8 KV, prompt cache 0, resident budget 20 GiB, the same model ID, the same four native shards, the same PLE shard, pack, MTP path, source commit/tree, engine binary SHA, and server bridge SHA. The run41 and run51 request histories are included per prompt in the evidence JSON.

The run41 and run51 config JSONs differ only in `args` and `log`. After removing run51’s explicit `--pool-affinity all` (the binary default), the argument arrays are equal; the environment dictionaries are byte-for-value equal. Run51’s engine log confirms that effective placement: both logs report 10 pool workers on logical processors `1,10,11,12,13,2,3,4,5,6`, host thread on processor 0, 33 automatic pool tasks per phase, 12,213 GPU cache slots (35.67 GiB), and 20.00 GiB resident and pinned RAM cache. Both report the same MTP draft load (839 MiB VRAM). Run-specific output logs and measured cache hit/read totals differ as runtime observations; they are not an identified cause. The separate [root control comparison](../20261011-51-worker-pool-sweep/root-control-comparison-01.json) also records matched effective controls and leaves cause unresolved.

Both process receipts name the same launcher virtualenv and the same `C:\Python314\python.exe` server child. Read-only PE version metadata for both current interpreter paths reports 3.14.8; the old receipts do not contain an interpreter version string or executable content hash, so the version is not independently snapshotted for each historical launch. Engine logs use local time: their `08:50` and `19:41` starts align with the corresponding UTC process records at `00:50` and `11:41` (UTC+8). Resource receipts report different monotonic baselines (about 1,842 s in run51 and 31,709 s in run41); neither admission record carries a boot ID, so the cause of that baseline difference is not established. No cross-run timing inference uses those clock values.

## KV adapter protocol note

The pinned `server.py` defines its generation stop set from `tokenizer.encode("<|im_end|>", parse_special=True)` and `tokenizer.encode("<|endoftext|>", parse_special=True)` (lines 2,673–2,674); it also lists `EOS_IDS = {248044, 248046}` (line 575). The actual small pack tokenizer config says EOS ID 248046 and padding/BOS ID 248044; its `vocab.json` maps `<|im_end|>` to 248046 and `<|endoftext|>` to 248044. Therefore the adapter can bind the request’s exact stop IDs as `[248046, 248044]` from the pinned bridge plus tokenizer metadata. `tail_role_token` reported in `INFO` is a separate prompt-tail value, not the generation stop set.

The engine protocol in `generate.cpp` provides `INFO ...` before `READY <context> stop`; `T <id>` output during `GEN`; and `DONE` at request completion. No `META` line is emitted by this pinned source. Its disk commands are `SAVE <path>` and `RESTORE <path>`, with `SESSION`/`SWAIT` progress and `SAVED <tokens> <bytes> <ms>` or `RESTORED <tokens> <bytes> <ms>` success replies; failures are `SERR ...` or `FATAL ...` (around lines 8,055, 8,128, and 8,711–8,918). The restore acknowledgement does not provide a pre-generation checkpoint-tail digest. The snapshot loader does validate the session header and payload checksum before accepting the payload (`conversation_file.cpp` lines 804–815 and 1,205–1,232), but that checksum is an internal 64-bit session hash, not a reported SHA-256 tail digest. `STRATA_STATE_HASH` is an opt-in post-request diagnostic, limited to prompt-cache mode, and prints 64-bit FNV fingerprints of selected state components. The KV-preparation configs set prompt cache 3 and enable this diagnostic, so post-request hashes can be compared with the reference after equivalent continuation. They still do not identify the state at the instant before that continuation. The draft currently sets `checkpoint_tail_sha256` to a SHA-256 of the text `tail=<FNV value>` after `GEN`; that field name would overstate what was measured. A truthful disk record can bind each immutable saved seed by its externally calculated full-file SHA-256 and size, recheck both before every restore, record `RESTORED` token/byte counts, then compare a bounded greedy continuation against the same continuation from an independent uninterrupted reference using actual `T` IDs, finish reason, and response length. Comparing post-continuation state hashes provides another parity check at that later point. This demonstrates continuation equivalence for the tested continuation; it does not prove byte-identical internal state at the checkpoint instant. Root should decide whether that evidence replaces the contract’s unavailable checkpoint-tail field or whether engine instrumentation is needed.
