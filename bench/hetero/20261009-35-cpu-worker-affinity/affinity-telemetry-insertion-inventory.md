The current CPU pool implementation files have not changed, but a full-model candidate still needs its own executable, model, runtime, config, and workload identity and model-level acceptance evidence.

In [`pool.cpp`](../../../src/kernels/cpu/pool.cpp#L347), `pin_this_thread` returns a Boolean. On Windows it directly returns `detail::set_thread_group_affinity`, which calls `SetThreadGroupAffinity` and returns true or false in [`pool_affinity_win.hpp`](../../../src/kernels/cpu/pool_affinity_win.hpp#L17). The pool constructor starts workers at [`pool.cpp`](../../../src/kernels/cpu/pool.cpp#L436): it initializes diagnostic `wstate_` values to `kParked` before creating threads, chooses each planned `core`, then the worker lambda calls `pin_this_thread(core, i)` and discards the return at line 461. No per-worker affinity result or readback is stored on `ExpertPool`.

Each worker enters `worker(id)` after the pin attempt and increments `parked_` before its first idle spin at [`pool.cpp`](../../../src/kernels/cpu/pool.cpp#L489). `wait_parked` observes all worker arrivals before a batch/phase at lines 564 and 835. That counter can show that workers reached the parked loop, but the initial `wstate_ = kParked` values are preinitialized diagnostics, not startup proof. A telemetry report should therefore use a separate per-worker startup status. Publish the status from the worker thread after the pin call and affinity readback, before entering `worker(id)`; use an explicit report-ready barrier (or the completed first parked barrier) before emitting an aggregate. Do not infer pin success from `wstate_`, a candidate list, worker count, or a successful kernel run.

For requested pins, the concrete Windows report can separate three facts: the `SetThreadGroupAffinity` return; an immediate `GetThreadGroupAffinity` readback of actual hard-affinity group and mask; and an optional `GetCurrentProcessorNumberEx` snapshot of the logical processor executing that worker at the moment of the snapshot. The last item is a point-in-time observation, not a lifetime guarantee. A singleton actual group mask can be mapped through the existing `GetSystemCpuSetInformation` lookup in `pool_affinity_win.hpp` to a numeric CPU Set ID. Keep the group/logical index, mask, CPU Set ID, and `EfficiencyClass` numeric; the current inventory intentionally does not label these P/E/LP.

Use distinct statuses such as `starting`, `not_requested`, `candidate_overflow_unpinned`, `set_failed`, `readback_mismatch`, `verified`, and `unknown_query_failed`. Keep planned IDs separate from observed IDs. The current Windows code reports only an error line on `SetThreadGroupAffinity` failure and otherwise discards the Boolean; the affinity test demonstrates a readback with `GetThreadGroupAffinity` in [`pool_affinity_test.cpp`](../../../src/kernels/cpu/pool_affinity_test.cpp#L127).

The host is a separate telemetry subject. `SessionLoopScratch::init` selects `planned_host_core()` with the default `All` mode, calls `pin_current_thread`, and stores whether `ThreadAffinity.valid` succeeded in [`session.cpp`](../../../src/core/session.cpp#L548); `free()` restores that saved placement at line 566. In contrast, `generate.cpp` constructs `ExpertPool` with `o.pool_affinity` at line 4267 and prints a planned host core using `detect_cpu_topology(true, o.pool_affinity)` at line 4280. Thus the printed candidate can differ from the host pin selected by `SessionLoopScratch` when `auto` or `p-cores` changes topology ordering. Record the session host pin API result and its own actual readback separately from worker results and from the printed candidate. The native microbench's `ScopedHostPin` is yet another caller-owned host pin and should remain labeled as harness-only.

The engine parser already accepts `--pool-workers` and `--pool-affinity` in [`generate.cpp`](../../../src/program/generate.cpp#L1728) and passes them to the pool. The startup log reports requested/actual-adjacent worker count and planned processor IDs at lines 4269–4287. The Monitor `INFO` line at line 8055 currently exports only `pool_workers` (the actual pool size), not requested count, affinity mode, host participation, or pin result.

The Python serve layer has no separate pool-affinity command-line parser. `StrataEngine` passes the run-config `args` through as `[exe, "--serve", *args]` in [`server.py`](../../../serve/server.py#L660). Its READY pump parses every `INFO key=value` field into `engine.info` at line 680; `/metrics` returns the complete `engine.info` object inside `engine` at lines 3072–3117. Therefore flat new INFO fields reach the monitoring API without a new server protocol. `v1_status` exposes only the engine version, and the current web Monitor renders selected known engine fields, so UI display would require a separate UI change. The Settings `EDITABLE` list in [`runconfig.py`](../../../serve/runconfig.py#L19) does not expose pool options; existing config `args` are forwarded unchanged.

Suggested flat startup fields are `pool_workers_requested`, `pool_workers_actual`, `pool_affinity_requested`, `pool_host_works`, `pool_worker_pin_status`, and per-worker compact reports containing worker index, candidate status, planned group/index/CPU Set ID, `SetThreadGroupAffinity` return, actual `GetThreadGroupAffinity` group/mask readback, readback-query status, and optional sampled current processor. Report host fields separately, for example `pool_host_pin_status`, `pool_host_planned_group/index`, and `pool_host_actual_selected_cpu_set_ids`. Use `not_requested`/`unknown` explicitly; do not treat missing telemetry as success. No telemetry code or production default routing was changed in this inventory.
