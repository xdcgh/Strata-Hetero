## Pool interface and topology

`include/strata/kernels/cpu/pool.hpp:68-80,134-186` exposes `PoolAffinity::{All,Auto,PCores}`, `CpuTopology`, and `ExpertPool(n_workers, pin, host_works, affinity, tasks)`. There is no `None` enum: the unpinned arm is `pin=false`, with an otherwise explicit policy value. Positive `n_workers` sets the background-thread count; `host_works=true` lets the caller also claim jobs. `run_split_multi_native(const NativeFmt&, ExpertJobMulti*, int)` is the pool entry point for native GGUF experts.

On Windows, `detect_cpu_topology` reads `GetLogicalProcessorInformationEx(RelationProcessorCore)` and encodes LPs as `group*64+processor` (`src/kernels/cpu/pool.cpp:58-178`). `All` uses one LP per core; for mixed numeric efficiency classes it orders the higher class first. `Auto` orders higher-class primaries, their siblings, then lower-class LPs; `PCores` omits the lower class. Worker threads alone are hard-pinned by `SetThreadGroupAffinity` (`src/kernels/cpu/pool_affinity_win.hpp`). `ExpertPool` does not pin the caller: with `host_works=true`, caller work remains OS-scheduled. Extra workers beyond the candidate list receive core `-1` and are unpinned (`pool.cpp:436-464`); any such case must not be described as strict policy affinity.

The latest saved host topology receipt is `bench/hetero/20261007-03-cpu-topology/hardware_cpu-review-02.json` (SHA-256 `86c3611b3c5d6064df32467990e6107c68ee59f77e1d1e80120e5f8bf6282596`), collected 2026-10-07 06:23 +08:00; it is not a fresh 2026-10-09 measurement. It records `GetSystemCpuSetInformation`, group 0, CPU-set IDs 256-271: `EfficiencyClass=1` at LPs 0,1,10-13; class 0 at LPs 2-9,14-15. P/E names are explicitly unverified. The pool implementation treats the maximum numeric class as its P-core candidate class; that software ordering does not prove physical P/E labels. A future run should record fresh `detect_cpu_topology(true, policy)` output before affinity cases.

## Native operator and current test coverage

`include/strata/kernels/cpu/native_expert.hpp` defines `NativeFmt`, `native_quant_act`, `native_gu_rows`, `native_quant_h`, and `native_down_rows`. The current `src/hetero/native_expert_bench.cpp:398-404` is a one-thread baseline using those calls, not `ExpertPool`. The saved native run uses Q4_K gate/up (type 12), Q5_1 down (type 7), H=2560/I=640, and `STRATA_KQ256=0`; its selected Q8_K activation quantizer is `q8k_quant_avx2`, down activation is ggml Q8_1. Existing build receipt: `bench/hetero/20261009-10-native-cpu/build/build-receipt.json`; native run status is `complete_with_quality_failures` only versus the different NumPy F32 reference, so the pool comparison should use the saved actual native-CPU outputs, never relax their unchanged quantized arithmetic.

`ExpertJobMulti` has `MAXT=8` token rows (`expert.hpp:134-139`). For one expert, rows 10 and 16 must be split into jobs of 8+2 and 8+8; each job references the same real blob and disjoint input/output rows. `run_split_multi_native` then performs native gate/up, the same native hidden quantization, and native down; it changes scheduling, not the kernels (`pool.cpp:759-788`). Existing `src/kernels/cpu/pool_tasks_test.cpp` checks bitwise task partitioning across worker/host/task settings but uses fixture weights/activations unless given a blob. `pool_test.cpp` covers the older packed `ExpertPool::run` path. `pool_affinity_test.cpp` tests Windows affinity restoration and mutates affinity while it runs; none was run here.

## Frozen 0.1.40.4 versus upstream v0.1.41

Compared frozen source ref `6674a0065fb96bacde33e3eb10f91a1df86f95f2` with upstream `fb58e0dbc8399662c0e47c76578c6e878b14f6cf`. The pool API/implementation, Windows affinity helper and `NativeFmt` header are byte-identical: `pool.hpp` SHA-256 `5f7e7ee3f48ce6505ad25975c320310e647551df3304a87052ce3c7e2b414936`; `pool.cpp` `f789078f1e14b6cf72bec5cacc2802d358ad82cbd7bf890f344a4a4a32158611`; `pool_affinity_win.hpp` `63a3e8d6346d2887b6e139638ad74ab5ce005be20f6c0d4664c16938a84abe6f`.

Upstream adds CPU prefill-sharing integration and chunk/loan sizing, but no `ExpertPool` API change. It moves CPU feature/oracle checks out of AVX-512-compiled `expert.cpp` and adds native format-support predicates; native quantizer/operator signatures and Q4_K/Q5_1 row arithmetic are unchanged. `tools/calibrate.py` now interleaves three PCIe/spec-floor sweep rounds, selects medians, and preserves earlier candidates if a later engine restart fails; it still does not sweep pool affinity. These are relevant version differences, not evidence for or against H21's failure.
